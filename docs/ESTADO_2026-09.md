# Resumen ejecutivo

Este informe documenta la **revisión y actualización de QHAWAY 2.0** realizada el
**1 de setiembre de 2026**. Se auditó el estado de los cuatro módulos, la frescura de
los datos, las dependencias del frontend y los pendientes bloqueados. Se aplicaron las
actualizaciones **accionables desde el entorno local** y se diagnosticaron con precisión
los bloqueos que dependen de terceros (MEF, INEI) o del VPS.

**Titulares:**

- ✅ **Datos del presupuesto MEF frescos al 2026-08-21.** El pipeline automático
  (GitHub Actions, `refresh-data.yml`) regenera los JSON de presupuesto de forma recurrente;
  la última corrida exitosa fue el **21 de agosto de 2026** (serie nacional 2012–2026,
  detalle distrital 2026).
- ✅ **Bug de fecha corregido.** `meta.json` mostraba `lastUpdate: 2026-06-11` porque el valor
  estaba **hardcodeado** en `etl/build_mef.py`; ahora es **dinámico** (fecha de la corrida) y
  `meta.json` se corrigió a **2026-08-21** (fecha real del último refresco).
- ✅ **Dependencias del frontend actualizadas** a sus últimas versiones seguras (dentro de
  rango semver); **0 vulnerabilidades**; el `build` de producción compila correctamente.
- ✅ **Servicios del IDE re-descargados en vivo** del Censo 2017 (agua, desagüe,
  electricidad, internet) — REDATAM operativo para las entidades *Vivienda* y *Hogar*.
- 🟠 **Riesgo próximo — API SQL del MEF caída (HTTP 404).** El endpoint
  `datastore_search_sql` de Datos Abiertos del MEF hoy devuelve **404 «Recurso no
  encontrado» para toda consulta**. Los datos publicados **no están en riesgo** (ya son del
  21-ago), pero **el próximo refresco automático fallará** hasta re-descubrir el nuevo
  contrato de la API. La ausencia de refrescos después del 21-ago es coherente con este corte.
- 🔴 **Educación (IDE) sigue bloqueada**: la entidad *Persona* de REDATAM CPV2017DI
  devuelve **HTTP 500 para todas sus variables** (no es un código mal puesto; es una caída
  server-side de esa entidad en INEI). El IDE permanece en **3 de 4 dimensiones**.
- ⏳ **Cubo granular 2024**: proceso alojado en el **VPS**, no accesible desde el entorno
  local de esta sesión.

# 2. Actualizaciones aplicadas en esta sesión

## 2.1 Corrección de la fecha de actualización (`meta.json`) — ✅ hecho

Se detectó que `meta.json` reportaba `lastUpdate: 2026-06-11` pese a que los datos se
refrescaban semanalmente: el valor estaba **hardcodeado** en `etl/build_mef.py` (línea 145).
Se cambió por `datetime.date.today().isoformat()` (dinámico) y se corrigió `meta.json` a
**2026-08-21**, la fecha del último refresco real. Así el sitio deja de mostrar una fecha
engañosa.

## 2.2 Dependencias del frontend (npm) — ✅ hecho

Se ejecutó `npm update`, llevando todos los paquetes a su última versión **dentro del
rango semver declarado** (patches y minors seguros). Resultado: **0 vulnerabilidades**,
`package-lock.json` actualizado, y el `build` (`tsc -b && vite build`) compila sin errores.

Se **dejaron deliberadamente sin subir** los *majors* con cambios incompatibles, que
requieren migración y pruebas dedicadas:

| Paquete | Actual | Major disponible | Motivo de no subir |
|---|---|---|---|
| tailwindcss | 3.4.x | 4.x | Reescritura de configuración/CSS |
| vite | 7.3.x | 8.x | Cambios de build/plugins |
| typescript | 6.0.x | 7.x | Posibles rupturas de tipos |
| @vitejs/plugin-react | 4.7.x | 6.x | Acoplado a Vite 8 |
| @types/node | 24.x | 26.x | Alinear con runtime de Node |

## 2.3 Índice de Densidad del Estado (IDE) — 🟢 servicios refrescados

# 3. Bloqueos y riesgos diagnosticados

## 3.1 Riesgo próximo — API SQL del MEF retirada (HTTP 404)

El ETL de presupuesto (`etl/build_mef.py`, `discover_annual.py`) consulta:

```
https://api.datosabiertos.mef.gob.pe/DatosAbiertos/v1/datastore_search_sql
```

Hoy ese endpoint devuelve **HTTP 404 «Recurso no encontrado» para toda consulta** (incluso
`SELECT ... FROM information_schema.tables`). El sitio base de Datos Abiertos sigue en línea
(HTTP 200), por lo que **el problema es específico de esa ruta de la API SQL**: cambió o fue
retirada, aparentemente **después del 21-ago-2026** (último refresco exitoso).

Impacto: **los datos publicados NO están en riesgo** (son del 21-ago). Lo que se rompe es el
**próximo** refresco automático: el `cron` de `refresh-data.yml` fallará hasta que se
re-descubra el nuevo contrato de la API. Nota adicional: los `resource_id` por año **rotan en
cada corte**, por lo que la solución debe pasar por `discover_annual.py` (o su reemplazo),
no por IDs fijos.

**Acción:** identificar la nueva ruta/endpoint de la API SQL del MEF (o el mecanismo
equivalente), actualizar `discover_annual.py`/`build_mef.py`, y validar una corrida.

## 3.2 Educación IDE — REDATAM entidad *Persona* caída (HTTP 500)

Diagnóstico preciso de esta sesión: se probaron **10 variables candidatas** de asistencia
escolar y edad (`Persona.C5P12`, `C5P14`, `C5P13`, `P08`, `C5AP4`, `ASISTENCIA`,
`C5P4`, `EDAD`, `C5P4_R`, `P03`). **Todas devolvieron HTTP 500** de forma idéntica,
**mientras que las entidades *Vivienda* y *Hogar* respondieron correctamente** en la misma
corrida (agua, desagüe, luz, internet: 1874 distritos cada una).

**Conclusión:** no es un código de variable equivocado — es la **entidad *Persona* del
REDATAM CPV2017DI que está caída server-side en INEI**. No es resoluble desde nuestro
lado. **Acción:** reintentar `python3 etl/build_ide.py` periódicamente; en cuanto la
entidad *Persona* vuelva, `ideEducacion` se poblará y el IDE pasará a **4/4**.

## 3.3 Cubo granular 2024 — proceso en el VPS

La descarga y proceso del cubo 2024 corre en el **VPS** (`/opt/qhaway-api`), fuera del alcance
del entorno local de esta sesión. Al terminar la descarga, correr en el VPS
`build_resumenes.py 2024` para que categoría/tipo-gasto/drill/cubo-n cubran 2024 + 2025.
